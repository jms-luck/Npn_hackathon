02 — Decision map

Why these technologies were chosen

Each component owns one type of problem. This prevents the vector database, graph database, or LLM from becoming an accidental source of truth.

NeedChoiceWhyWhy not the obvious alternative
Transactional hiring dataPostgreSQL

Foreign keys, uniqueness, transactions, indexing, and mature operational tooling.

A document store would weaken cross-entity integrity for applications, resumes, jobs, and interviews.

API and authorizationFastAPI + SQLAlchemy

Typed contracts, dependency-based RBAC, async-ready HTTP, and clear ORM ownership.

A large full-stack framework would add conventions without improving this API-centric boundary.

Role-based interfaceReact + Vite

Fast development, route protection, reusable views, and a small production bundle.

Server templates would make the interactive admin, graph, upload, and filtering workflows harder to maintain.

Resume binariesAzure Blob Storage

Private object storage, content types, lifecycle support, and expiring SAS access.

Storing PDFs in PostgreSQL would inflate backups and database I/O.

Semantic retrievalQdrant + cosine distance

Purpose-built HNSW nearest-neighbor search, metadata payloads, and efficient top-K ranking.

SQL text search finds words, not meaning; PostgreSQL should not carry millions of high-dimensional vectors here.

Relationship explanationNeo4j

Candidate, resume, job, company, and skill relationships are naturally traversable and visual.

Deep relational joins can answer the question, but do not communicate the relationship structure as clearly.

Hot response accelerationRedis

Low-latency cache, atomic rate limits, TTLs, and fail-open behavior.

Process memory would diverge across replicas and disappear during restarts.

Embeddings and narrativesAzure OpenAI

Managed model deployments, strong embedding quality, and enterprise controls.

A locally hosted model would increase GPU, scaling, patching, and observability work.

05 — Data model

Relational records first

Stable numeric keys maintain database integrity. Human-facing IDs such as JOB_025 are presentation values, not replacement keys.

Useridentity · role · active state
1:1
Candidate / Recruiter / Interviewerrole-specific profile
1:N
Resume / Job / Applicationversioned evidence and submission
1:1
Interview / Match resultassessment and explainability
Why keep resume versions?

An application must continue pointing to the exact resume submitted at that time. Replacing one mutable resume would rewrite historical evidence and make audit results unreliable.

Why keep a global applicant pool?

Global candidates are stored once in global_applicants. Materializing every candidate against every job would create billions of rows; recruiter queries merge explicit applications with the global pool on demand.

Why are public IDs derived?

Prefixes make support and UI conversations clearer while preserving all existing primary keys and foreign keys. The formatter and parser are isolated in public_ids.py.

06 — User workflows

Four roles, four constrained workspaces

Candidate
  1. Registers and optionally adds social profiles.
  2. Uploads a validated resume.
  3. Receives Qdrant-ranked job recommendations.
  4. Reviews active jobs and applies with one resume version.
  5. Tracks applications and DSA evidence.

Why: the candidate controls which evidence is submitted for each role.

Recruiter
  1. Registers with a company verification code.
  2. Creates and publishes roles.
  3. Uploads applicants in bounded batches.
  4. Ranks candidates by resume-to-job similarity.
  5. Opens explainable skill and relationship graphs.
  6. Schedules interviews.

Why: company ownership is resolved from the authenticated profile, never trusted from request input.

Interviewer
  1. Registers against a verified company.
  2. Views only assigned interviews.
  3. Opens “Why suitable?” evidence.
  4. Submits score and feedback.

Why: interviewers need focused evidence, not administrative access to the full talent pool.

Administrator
  1. Reviews platform datasets.
  2. Manages companies and verification codes.
  3. Controls user activation and records.
  4. Uses secure resume access.
  5. Searches the readable audit trail.

Why: operational powers are isolated behind an explicit admin role and audited routes.

07 — Resume pipeline

Validate before storage, derive after commit

  1. 01

    Receive the file

    Candidate or recruiter uploads PDF/DOCX through a bounded multipart endpoint.

    Why: limits are enforced before expensive parsing, network, or model calls.

  2. 02

    Verify actual structure

    PDF signature, encryption, and page limits are checked. DOCX ZIP structure, compression ratio, paths, macros, ActiveX, and embedded objects are validated.

    Why: a filename extension and browser MIME type are attacker-controlled metadata.

  3. 03

    Extract bounded text

    PyPDF and python-docx extract plain text with a character ceiling.

    Why: bounded evidence protects memory, prompt size, embedding cost, and downstream logs.

  4. 04

    Store privately

    The binary is written to a private Azure Blob container under a generated candidate/version path.

    Why: opaque paths prevent filename collisions and keep binaries out of PostgreSQL.

  5. 05

    Commit metadata

    PostgreSQL stores filename, Blob path, version, parsing status, extracted text, and candidate ownership.

    Why: durable relational ownership must succeed before optional indexes.

  6. 06

    Build derived evidence

    The text is embedded once and upserted into Qdrant; missing social profiles may be canonically extracted.

    Why: vector failures must not erase an already durable resume.

08 — AI matching

Meaning becomes a searchable vector

Candidate matching is retrieval, not an autonomous hiring decision.

Input AResume text
→
Modeltext-embedding-3-large
→
Representation3,072 dimensions
→
IndexQdrant HNSW
→
OutputTop 50 active jobs
cosine similarityscore = (resume · job) / (||resume|| × ||job||)

Closer vector direction means stronger semantic similarity, independent of document length.

Candidate → jobs

The stored resume vector queries the global job_embeddings collection. Qdrant compares it against every indexed active job and returns top-K IDs; PostgreSQL then supplies current job/company details.

Job → applicants

The job vector queries a job-specific applicant collection. Canonical resume vectors are copied into that collection to avoid repeated Azure embedding calls.

Important

“All jobs” means all jobs present in Qdrant. Startup preflight compares PostgreSQL active-job count with Qdrant points and reports incomplete coverage before users rely on recommendations.

09 — Evidence enrichment

Extra signals are bounded and explainable

GitHub project relevance

The public profile URL is canonicalized, GitHub’s fixed API host is queried, and repository names, descriptions, topics, and languages are compared with resume project terms.

Why: repository metadata can support project claims, but cannot prove account ownership. Its influence is capped at 15%.

LeetCode DSA strength

A fixed GraphQL endpoint returns difficulty and topic counts. Weighted core topics plus Easy/Medium/Hard depth produce a transparent 0–100 score.

Why: published targets and topic bars are easier to challenge than an unexplained model label.

LLM narrative

A model summarizes evidence only after numeric retrieval. Resume/job text is serialized as untrusted JSON and output must pass a one-field plain-text schema.

Why: narrative improves readability, but malformed or injected output falls back to deterministic text.

11 — Security

Controls at every trust boundary

Identity

JWT + Argon2 + database RBAC

Tokens identify users; current role and active status come from PostgreSQL. Company/candidate ownership is never accepted from client claims.

Uploads

Content verification

Signature, structure, decompression, macro, path, size, page, encryption, and extraction limits run before storage.

Files

Private Blob + SAS

Only authorized users receive short-lived read URLs. Storage credentials never reach React.

AI

Prompt and output boundaries

Evidence is untrusted JSON. Output rejects HTML, URLs, extra fields, control characters, and oversized content.

Abuse

Redis rate limits

Login, registration, upload, matching, and profile checks use distributed atomic counters and auditable 429 responses.

Network

SSRF-resistant clients

GitHub and LeetCode calls use fixed HTTPS hosts. User input selects only a validated username.

Browser

CSP and response headers

CSP, frame denial, MIME protection, referrer and permissions policy, HSTS, and no-store sensitive responses.

Audit

Structured, PII-aware logs

Request ID, actor, role, route, status, outcome, duration, and masked network are recorded without bodies or secrets.

Administrator bootstrap

No universal admin credential exists in source. Initial email and a 12+ character password must be supplied through environment configuration.

12 — Performance

Spend latency where it creates value

30 spublic job cache
5 mincompany cache
5 mingraph cache
1 hourGitHub evidence cache

Optimizations used

  • HNSW approximate nearest neighbors
  • Canonical resume-vector reuse
  • Batched embedding and Qdrant upserts
  • Redis JSON and raw response caches
  • Gzip for large API/static responses
  • Server-side pagination and filtering
  • Database indexes on joins/filter columns

Failure behavior

  • Redis failure: continue from PostgreSQL
  • Neo4j failure: return relational graph
  • Qdrant failure: return clear unavailable state
  • LLM failure: deterministic explanation
  • Post-commit indexing failure: keep durable resume

Repeat local measurements with python scripts/benchmark_http.py. Performance should be judged with the background seed status recorded because imports compete for database and network resources.

13 — Data seeding

Source first, indexes second

  1. 01

    Companies

    python scripts/import_companies.py

    Upserts normalized company records and generates missing verification codes.

  2. 02

    Jobs

    python scripts/import_jobs.py

    Resumable chunks populate PostgreSQL. Checkpoint prevents restarting millions of rows.

  3. 03

    Applicants and Blob files

    python scripts/import_dummy_applicants.py --workers 8

    Creates role records, resumes, global pool entries, and private Blob objects.

  4. 04

    Resume vectors and job collections

    python scripts/seed_docker_qdrant.py

    Rebuildable Qdrant indexes are derived from parsed PostgreSQL resumes.

  5. 05

    Global job vectors

    python scripts/generate_job_embeddings.py

    Runs only after job import so every active job can participate in candidate recommendations.

  6. 06

    Neo4j

    python scripts/seed_neo4j.py

    MERGE-based relationships are idempotently derived from authoritative records.

Why startup does not seed by default

Embedding millions of jobs can run for hours and incur Azure cost. Container preflight reports seed_* versus rebuild_*; automatic seeding requires explicit opt-in.

Why external state: PostgreSQL, Blob, Qdrant, Neo4j, and Redis have independent persistence, scaling, backup, and upgrade requirements. Packing them into the application image would make deployments fragile and data lifecycle unsafe.

16 — Operations

Know what is healthy and what is complete

Health

Audit

logs/audit.log

Admin UI offers search, filters, readable actor/outcome fields, and detailed request context.

Seeding

Performance

scripts/benchmark_http.py

Measure p50/p95 and concurrent throughput from the deployed runtime.

Definition of done

A deployment is ready when:

  • Schema and migrations are applied.
  • Health and protected-route checks pass.
  • PostgreSQL active jobs equal Qdrant job vectors for complete matching.
  • Parsed resumes are covered by resume vectors.
  • Neo4j preflight is available or fallback is explicitly accepted.
  • Frontend lint/build and backend tests pass.
  • No real secrets or datasets are committed.
